## Implementation steps

1. Replace admin tab identifiers with stable internal IDs, then translate their displayed tab text and ARIA labels. Do not compare localized labels for tab selection.
2. Translate dashboard labels, login/logout states, settings labels/help/status/errors generated by frontend validation, sync summaries, controls, and the HTML/ad editor UI.
3. Leave actual configuration values intact, including the editable language code, domain rules, URLs, JMAP token, user-provided HTML/CSS/ad names, and API-returned error detail.
4. Use locale-aware formatting for dashboard/sync timestamps and number-bearing status text while preserving testable state transitions and CSRF/API payloads.
5. Update the admin test fixtures and assertions for English defaults, then add a Vietnamese render/switch coverage case that exercises tab labels and a representative form/status label.
6. Run the focused suite and production build. If the known installed-font resolution failure remains, record it separately; do not change dependencies merely to work around it.

## Success criteria

- Every administrator chrome string is catalog-backed and controls retain their current keyboard/ARIA semantics.
- Localizing a tab cannot break `activeTab`, roving tabindex, or component selection.
- Focused tests pass and the production build is attempted with its exact result recorded.

## Risks and safeguards

- Tab labels currently double as state values, so converting them to IDs is required before translation; this is the only structural refactor.
- The General language field is a locale code, not translated prose. Its help text should state supported values rather than masking an unsupported value.
